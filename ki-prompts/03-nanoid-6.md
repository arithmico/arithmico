# Migration prompt: nanoid 3 → 6

## Context to give the assistant

You are working in the `packages/services/api` workspace of the `arithmico` monorepo, a NestJS 11 application. It currently depends on `nanoid` `^3.3.19` and consumes it via a CommonJS `require`/`import` in a TypeScript codebase compiled with `ts-loader`/`tsc`, not bundled with an ESM-aware bundler.

## Task

Upgrade `nanoid` from 3 to 6.

1. Read the `nanoid` changelogs for versions 4, 5 and 6. The key breaking change across all three is that `nanoid` became a pure ESM package starting with version 4, dropping the CommonJS build entirely. Version 5 raises the minimum Node version, and version 6 continues the ESM-only direction with minor API cleanups (check the changelog for any renamed exports, e.g. changes to `customAlphabet` or `customRandom`).
2. Find every usage of `nanoid` in `packages/services/api/src` and `packages/services/api/apps` (if present) with a search for `from 'nanoid'` and `require('nanoid')`.
3. Since the api workspace's build output is CommonJS, either:
   - Confirm whether the current `tsconfig.json` / NestJS build already targets ESM output (`"module": "esnext"` or similar with `"type": "module"` in `package.json`); if yes, importing `nanoid` normally is fine, or
   - If the build stays CommonJS, replace static imports of `nanoid` with a dynamic `await import('nanoid')` at the call sites, or introduce a small wrapper module that isolates the dynamic import so the rest of the codebase does not need to change, or
   - As a fallback if dynamic import is impractical at the call sites, evaluate pinning to the last CommonJS-compatible `nanoid` 3.x release instead of upgrading, and document that decision instead of forcing the upgrade.
4. Do not change generated ID formats or lengths unless the changelog documents a default alphabet or length change that must be explicitly opted out of to preserve existing ID formats (relevant if any generated IDs are persisted, e.g. in MongoDB documents).
5. Do not modify test files; if tests mock `nanoid`, ensure the mock still matches the real module's export shape after the upgrade.

## Validation checklist

- `npm run build -w api` succeeds.
- `npm run test -w api` passes with the same test count as before.
- Manually verify (or add a small script) that IDs generated by the upgraded module have the same length and alphabet as before, if any persisted document relies on the current ID shape.
- No remaining CommonJS `require('nanoid')` call that would fail at runtime under the new package.
